# Design

## Context

- **Factory blocks** (`crates/core/src/factory.rs`) are entities on a marker tile with a `FactoryBlock { kind, facing }`. `factory::run_due_steps` runs one step per 20 ticks, wherever blocks are. `Game::factory_neighbor` reads neighbors across chunk edges.
- **Fluid tiles:** sprite folders and `PaletteKey` entries exist for water, oil, blood, acid and lava, but the core has no fluid model.
- **Power** comes from `add-power-grid` (generators, poles, a per-consumer power fraction).
- **Crafting** (`add-crafting-tree`) requires every placeable item to be craftable from raw sources, and its test enforces that.
- **Worldgen:** `GameWorld::generate_chunk` builds tiles from Perlin noise per chunk. Structures are queued and applied when a chunk is first needed.

## Goals / Non-Goals

**Goals:** a unique, steady metal source; the smallest fluid model that supports it; an early unpowered path through scooping.

**Non-Goals:**
- Fluid physics on tiles (flowing lava).
- Per-pipe pressure or flow simulation (networks act as one shared buffer).
- Copper and other ores beyond defining the enum.
- Temperature.
- Spouts running dry permanently.

## Decisions

### Spouts are factory entities placed by worldgen
A spout is a `FactoryBlock { kind: OreSpout }` entity with `OreSpout { ore }` and a `FluidTank`.
- **Placement:** worldgen decides spout positions with `new_rng(chunk)`. Entities can't be spawned from `generate_chunk`, which only builds tiles, so the chunk gets a `TileKind::SpoutSite` marker.
- **Spawning:** the first time the chunk is ensured (the same path that applies pending structures), each marker becomes a spout entity. This keeps "generated by a machine" and "generated by walking" identical.
Alternative: spouts as a special tile with a side table. Rejected: the reservoir is state, and state lives on entities so it's saved and stepped like everything else.

### Placement chance
One constant, `SPOUT_CHANCE_UNDERGROUND`, sets the chance per underground chunk. Surface chunks use half of it (`SPOUT_CHANCE_UNDERGROUND / 2`). Surface spouts go on a passable ground tile, never inside a structure's footprint.

### Fluids
- `FluidKind { MoltenIron }`, with `MoltenCopper` reserved.
- `FluidTank { fluid: Option<FluidKind>, amount_mb: u32, capacity_mb: u32 }`.
- Starting capacities: spout 1000 mB, basin 400 mB, crucible 100 mB.
- One helper, `transfer(from, to, max)`, enforces kind and room. Pumps and scooping both use it.

### Pipe networks
Pipes are `FactoryBlock { kind: Pipe }` entities. Each pipe has a `FluidTank` of 100 mB, so saving and breaking need no separate network state.
- **Networks** are the connected groups of pipes in the four cardinal directions. They are rebuilt only when a pipe is placed or broken, and cached on `Resources` like the factory index (derived data, rebuilt on load).
- **Delivery:** each step a network acts as one buffer.
  - Its fluid is the sum over its pipes.
  - Pumps facing into any of its pipes add to it.
  - It then delivers to the adjacent machines with a `FluidInput`, ordered by position, up to `PIPE_THROUGHPUT_MB` per step (40 mB to start).
  - Afterwards its contents are spread back evenly over its pipes, with the remainder going to the lowest-positioned pipes first.
- **Determinism:** fixed position order for delivery, and a fixed order when spreading the contents back.
- **Breaking a pipe** drops that pipe's tank (lost fluid), then splits the network.

Alternative: per-pipe flow from fuller to emptier neighbors. Rejected for now: it needs many steps to cross a long line and is harder to reason about; the shared-buffer model matches how power networks work.

### Machine fluid input
`FluidInput { accepts: &'static [FluidKind] }` marks a machine side that takes fluid; it uses the machine's own `FluidTank`. Pumps facing a machine directly and pipe networks both deliver through it, so later processing machines (for example, a refinery) only need the component.

### Step order
Spout fill → power distribution (from `add-power-grid`) → pumps → pipe networks → basins. Pumps read power from the step's distribution, the same way machines do.

### Numbers (tunable)
- Spout: fills 5 mB per step (25 mB per game second), so empty to full takes 40 game seconds.
- Pump: moves 20 mB per step while fully powered, scaled down by the network's power fraction.
- Basin: cools for 10 game seconds per ingot.

### Early game
The crucible is an item that records its contents (empty or full of a fluid). Scooping and pouring go through the interaction system with a new `InteractionType` for each, so the Choose Interaction menu and the context help panel list them.

### Unbreakable
`mining_drop` has no entry for the spout, and the mining system checks `FactoryKind::breakable()` before breaking factory blocks.

## Risks / Trade-offs

- [Spouts too rare or too common] → The placement chance is one constant, and a test counts spouts over a fixed area for a fixed seed, underground and on the surface, so tuning and the 2:1 ratio are visible.
- [Crucible state as an item] → Two item kinds (`Crucible`, `CrucibleMoltenIron`), not item metadata, so inventories stay simple.
- [Pumps need power before belts exist] → Scooping covers the early game, and basins fall back to keeping ingots or using a chest.
- [Large pipe networks rebuilt often] → Rebuilt only on place or break, not every step; a test times a 500-pipe rebuild.
- [Fluid lost when breaking a pipe] → Matches the Factorio feel; the message log says how much was lost.
